# Xshell batch import, credential retention and deferred verification

User requests bulk Xshell import, reusing saved passwords, and an explicit choice to add temporarily unreachable connections. These behavior changes supersede the earlier metadata-only/strict-verification import requirements.

- Accept multiple files, directories of .xsh files, and ordinary ZIP/.xts exports. Bound uploads to 1024 files/candidates and 16 MiB total; archive members remain individually bounded and links/traversal/bombs rejected. The authenticated import preview route alone may accept JSON up to 24 MiB; other requests retain their 1 MiB cap.
- Parse secrets only locally. `parse_import_files(..., credentials=None, credential_sink=None)` never returns plaintext/ciphertext secrets. A caller-supplied sink receives `(candidate_id, descriptor)` after safe candidate IDs are assigned. Descriptors contain `password` when decoded, or `encrypted_password/version` when not decoded. Public metadata includes `credential_status` and `has_imported_password`; no secret prefills.
- One optional Xshell master password or source Windows username/SID can unlock a batch. Use a mature optional cipher library, verified digest checks and documented version algorithms; unsupported/missing/wrong material yields an explicit status. Never guess a missing identity, silently treat ciphertext as plaintext, or brute-force. Source files remain unmodified.
- Preview secrets/descriptors live in bounded process memory with ten-minute expiry. Successful imports retain login credentials in OS keychain; only opaque references enter connection state. Unknown encrypted credentials may also be retained in keychain for later recovery. Never plaintext fallback, argv/log/audit/HTTP secret reflection or Git fixtures with real data.
- First commit attempts normal verified creation. Failure returns `can_add_unverified:true` for valid nonconflicting rows. UI offers an explicit per-batch/per-row confirmation. Only a second commit with strict `allow_unverified:true` invokes `create_unverified`.
- `create_unverified(body)` has no network side effects. It preserves connection metadata and available credential/key material as `installed:false, usable:false, verification_status:pending`. Existing aliases are never overwritten. Missing credentials do not prevent explicitly confirmed metadata registration.
- Existing test action for a pending connection uses saved login credentials to establish/verify key access; only successful verification activates the alias. Failure retains pending state and credentials. Existing instructions to use only `usable:true` still apply.
- UI sends commits in small batches (ten rows), shows progress and per-row results, retains failed selections and provides deferred-add confirmation. Recovered credentials are used server-side, never returned to the browser.
- All automated verification uses temporary HOME, fake SSH/keychain and synthetic encrypted session fixtures. Do not import real user sessions or call real servers. Update agent/user docs and release allowlist, then verify the installed local UI and publish a new version under the existing release authorization.

Ownership: credential parser/crypto agent owns imports + new xshell crypto module/tests; SSH agent owns SSH entrypoint + new pending module/tests; UI agent owns app JS/CSS and frontend source tests; root owns admin/kernel APIs, integration tests, installer/dependencies, docs, packaging and whole-system verification.
